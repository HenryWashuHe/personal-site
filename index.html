    A messaging bar in the friend feed

    live after A/B test

    The goal was to replace the bottom action area of the friend feed's video page with a messaging bar, so you could reply, tap a suggested emoji or start a voice message without leaving the video. I owned most of the Android client.

    • Four explicit states. Server signals on each video map to one client decision: keep the default bar, show the new bar with voice, show it without voice, or leave the area empty on purpose. Separate booleans would have let "can't show messaging" quietly turn into "show nothing."
    • Module boundaries. The feed module owns the UI and lifecycle. The messaging module owns sending, quick reply, emoji suggestions and the half-screen chat. I connected them through the messaging module's exported interfaces instead of its internals, and reused the existing quick-reply flow rather than rebuilding it.
    • Checking the contract before reusing code. An older feed presenter looked reusable, but its bind method was final and cast the model to a different type, which meant a compile error or a runtime cast failure. I built on the detail-page presenter instead.
    • Lifecycle under view reuse. The page reuses a visible view before binding the next video asynchronously. I cleared the previous video's context before each bind so a stale view can't take a click, removed observers on unbind, and only logged an impression once a page was actually selected.
    • A crash in an optional cache. Emoji suggestions read a Fragment-level cache, but this page can have no Fragment. I traced the null from a Java getter through Kotlin's platform types, made the cache optional, and kept the network request going.
    • A bug only the control group could see. During rollout, control users got an empty bar on their own videos. A content rule ran before the cohort check. The fix was 36 lines: check the cohort first, plus a remote switch so the fix itself could be rolled back without a new release. Try it below.

    COMET

    Co-optimizing memory efficiency and test-time compute. Fall 2026, in progress.

    Agents run long, and their KV cache grows with every step. Compressing the cache frees memory and compute for more attempts at a task, but extra attempts only help if what's left in the cache is still enough to solve it.

    COMET asks how to split a fixed inference budget between keeping memory, taking more attempts, and paying to recover what was thrown away. Four of us are building it for Dr. Kaoutar El Maghraoui's graduate seminar on scaling LLM systems, and I own experiment setup and execution.

    The questions

    Can a recovery trigger based on things the agent can observe, its context length and tool-call count, beat never rebuilding and rebuilding on a fixed schedule? And at 80, 50 and 25% retention, how much does one rebuild per attempt buy back compared with full-cache best-of-N under the same budget?

    The setup

    Qwen3-8B in BF16 on AppWorld, whose multi-step agent tasks have outcomes that can be checked deterministically. One A100 80GB, batch size 1, sequential attempts, on an extended Mini-SGLang engine. A pilot on train and dev tasks freezes every budget, cap and seed before anything touches the test set.

    The first experiment

    Every run branches from the same saved checkpoint of the agent and its environment, taken before compression. Each branch keeps 100, 80, 50 or 25% of the cache entries full-cache inference would hold at that step, then plays out on its own, so retention is the only thing that differs.

    How a rebuild works

    A rebuild re-prefills the attempt's full raw transcript and then reapplies the eviction policy. It never undoes tool actions. Rebuilds count against the same time and VRAM budget as everything else, and a rebuild that can't fit under the memory cap isn't allowed.

    Four ways to manage the cache, all running in one engine
    MethodWhat it keepsWhat it tests
    Full KVEverything, in BF16Baseline success and cost, plus best-of-N with the same budget
    StreamingLLMAttention sinks and the most recent tokensWhether recent observations are enough, and whether more attempts make up for lost history
    R-KVTokens that are important and not redundantWhether keeping useful reasoning states preserves the benefit of sampling more
    AgentKVPhase-aware, agent-specific retentionWhether early evidence survives until the later actions that need it

    What we measure

    • Oracle task success: the share of tasks solved by any of up to N attempts within budget
    • Single-attempt success and how many attempts actually ran
    • End-to-end latency, decoding throughput and estimated FLOPs
    • Peak KV-cache memory, including transient spikes during rebuilds
    • Paired comparisons across seeds, with bootstrap confidence intervals over tasks

    Distributed systems, in Go

    One key-value store, rebuilt five times. Each version survives more failure than the last, ending in the same basic architecture behind Spanner and most modern storage systems.

    1. MapReducedone

      A MapReduce library in Go. The master hands out map and reduce tasks and reassigns any whose worker dies. That's safe because workers are stateless, which is the simplest kind of fault tolerance there is.

    2. Primary/backup key-value serverdone

      The first stateful server. The primary forwards each operation to a backup before replying, and when the primary dies the backup takes over without losing acknowledged writes. Getting the handoff right is where the bugs live.

    3. Paxos key-value storedone

      Replicas agree on every operation through Paxos and apply the same log in the same order. The store stays consistent through crashes and dropped or delayed messages, and keeps serving as long as a majority is up. Retried client requests take effect once.

    4. Sharded key-value storedone

      The Paxos store split into shards across many replica groups, with a replicated configuration service that moves shards between groups while clients keep reading and writing. This is the step from fault tolerant to fault tolerant and scalable.

    5. Model checking Paxosdone

      A bare-bones model checker that explores message orderings and failures to check that Paxos never decides two different values. Testing shows the bugs you thought of; model checking finds the ones you didn't.

    Research

    Interpretability, mostly

    • Models sometimes get drug-toxicity questions right for the wrong reasons. I wanted to know whether a model actually represents the chemistry, or is matching surface cues that happen to line up with the answer.

      What I did

      Extracted residual-stream activations on drug-toxicity benchmarks and trained linear probes on them to see how scientific concepts are laid out inside the model. Then I tried to break the probes, varying prompts and contexts and building adversarial examples meant to pull the real concept apart from the cues.

      Why it matters

      A probe with high accuracy isn't evidence of understanding if it's tracking a spurious feature. Measuring probe sensitivity and concept separability under pressure is how you tell the two apart.

      RemotePyTorchInspect AIresidual streamlinear probes

    • Does retrieval-augmented generation switch on reusable reasoning routines inside a model? I tested that with sparse autoencoder features on Gemma-3-27B at Columbia's Complex Resilient Intelligent Systems Lab.

      Setup

      Gemma-3-27B with pretrained SAEs from SAE-Lens on a Slurm GPU cluster. I built the PyTorch and Hugging Face Transformers pipelines for inference and evaluation, and used torch.profiler to keep the GPU jobs efficient.

      What happened

      One candidate feature passed ablation and differential-activation tests: removing it changed behavior, and it activated differently with retrieval than without. It then failed a pre-registered steering-specificity test. Turning it up didn't specifically produce the behavior.

      What I took from it

      Necessary isn't the same as sufficient. Following Makelov et al., a feature can matter when it's removed without being what drives the behavior on its own. That gap is exactly why the steering test was pre-registered.

      Earlier in the semester I used PCA, normalization and probing to compare how the model represents the same math problems posed in plain language and in symbols, with controlled accuracy benchmarks across both formats.
